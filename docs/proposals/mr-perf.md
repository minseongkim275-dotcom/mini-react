# 제안서: 성능 엔진(mr-perf) 관점

기준: `dev` 6853949. 측정 도구: `scripts/bench/run.js` (Node 22 + jsdom 26, 의존성 추가 없음).
원자료: `docs/bench/baseline-6853949.json` (1k, 11회 중앙값), `docs/bench/baseline-6853949-10k.json` (10k, 3회).

## 1. 기준선 측정

행 구조는 js-framework-benchmark와 같다. `<tr key><td>id</td><td><a onClick>label</a></td><td><a onClick>x</a></td></tr>`.
**핸들러는 실제 앱처럼 렌더마다 새 화살표 함수**다(mr-lead 기준선과 다른 점. 이 차이가 아래 1번 발견을 만든다).
시간은 `diff()` + `patch()` 한 번(준비 단계 제외). 패치 수·변경 기록 수는 결정적, 시간은 jsdom이라 참고용이며 실행마다 ±30% 흔들린다.

| 시나리오 (1k행) | 전체 ms | diff ms | patch ms | 패치 수 (종류) | DOM 변경 기록 |
|---|---:|---:|---:|---|---:|
| 생성 (이전 트리 없음) | 113 | 2.1 | 111 | 1 (CREATE 1) | 1 |
| 생성 (빈 tbody에) | 160 | 3.2 | 157 | 1000 (CREATE) | 1000 |
| 전체 교체 | 176 | 5.5 | 169 | 2000 (REMOVE 1000, CREATE 1000) | 2000 |
| 10행마다 갱신 | 24 | 21.7 | 2.7 | **2100** (TEXT 100, **PROPS 2000**) | 100 |
| 한 행 선택(class) | 31 | 27.7 | 2.4 | **2001** (PROPS) | 1 |
| 두 행 swap | 26~58 | 23~49 | 3~6 | 2002 (PROPS 2000, MOVE 2) | 4 |
| 맨 뒤를 맨 앞으로 | 27 | 22.4 | 2.5 | 2001 (PROPS 2000, MOVE 1) | 2 |
| 뒤집기 | 96 | 19.4 | 75 | 2999 (PROPS 2000, MOVE 999) | 1998 |
| 한 행 삭제 | 41 | 38.7 | 2.9 | 1999 (PROPS 1998, REMOVE 1) | 1 |
| 1k 뒤에 1k 추가 | **521** | 47.9 | **466** | 3000 (PROPS 2000, CREATE 1000) | 1000 |
| 같은 데이터로 다시 렌더 | 22 | 17.6 | 1.2 | **2000** (PROPS) | **0** |
| 전체 지우기 | 23 | 1.6 | 21 | 1000 (REMOVE) | 1000 |

### 읽은 것 (근거 수치)

1. **핸들러 때문에 렌더마다 PROPS 2,000개가 생기고, 그중 실제 DOM을 바꾸는 것은 0개다.** 같은 데이터로 다시 그려도 패치 2,000개.
   `diffProps`가 함수를 `Object.is`로 비교하는데 화살표 함수는 매번 새것이다. patch는 핸들러 표만 바꾸므로 DOM 변경 기록은 0.
   → 학습 페이지의 패치 목록이 "바꾼 것"이 아니라 소음으로 가득 찬다. "바뀐 부분만 고친다"는 설명과 숫자가 어긋난다.
2. **갱신 시나리오의 시간은 거의 전부 diff다** (10행마다 갱신: diff 21.7 / patch 2.7ms). DOM이 1개만 바뀌어도 diff가 18~28ms.
   CPU 프로파일(같은 데이터로 60회 다시 렌더) 자기 시간 상위: `createVNode` 588ms(GC 648ms 별도), `diffChildren` 477, `own` 241, `collectNodes` 193, `hasDuplicate` 172, `diffNode` 159.
   - `createVNode`의 `Object.defineProperty(dom)`: 마이크로벤치 700k개 생성 **315~677ms vs 20~28ms(일반 속성) vs 67~88ms(class `#dom` 비공개 필드)**. 즉 8~15배.
   - `diffChildren`은 자식 3개짜리 `<tr>`에도 Map·Set·이름 문자열·LIS 배열을 만든다. 행 1000개 × 이 비용.
   - `collectNodes`는 diff마다 이전 트리 전체(약 7,000노드)를 Set에 담는다.
   - 핸들러를 고정 함수로 바꾸면 같은 데이터 diff가 14.2 → 12.4ms(-13%). 즉 1번은 시간보다 **패치 수·설명의 정직성** 문제다.
3. **살아 있는 부모에 하나씩 넣는 CREATE가 비싸다.** 같은 1,000행이 이전 트리 없이 한 번에 들어가면 111ms(변경 기록 1), 빈 tbody에 하나씩이면 157ms(기록 1000), 1k가 있는 tbody에 1k를 덧붙이면 466ms(기록 1000).
4. **전체 지우기 1,000건, 전체 교체 2,000건**: 행마다 DOM 연산 한 번.
5. 이미 최소인 것: swap(MOVE 2, 기록 4), 맨 뒤→맨 앞(MOVE 1), 한 행 삭제(REMOVE 1), 뒤집기(MOVE 999 = n-1, 이론 최소). LIS 덕분이다. 여기는 손댈 필요 없음.

## 2. 특화 분야 제안

**"대량 목록에서 하지 않아도 될 일을 하지 않는 엔진, 그리고 그것을 숫자로 보여 주는 벤치마크"**

mr-lead의 A안("최소 DOM 변경을 증명하는 엔진")에 동의하고, 범위를 한 단계 넓힌다.
DOM 변경 수(결정적)만 보면 갱신 시나리오는 이미 최소다. 남은 낭비는 **(1) DOM에 아무 영향이 없는 패치, (2) diff 자체의 할당·순회, (3) 연속 삽입·전체 삭제의 DOM 연산 횟수** 세 가지다.
그래서 지표를 셋으로 고정한다: **패치 수 = 실제로 바꾼 것 수**(소음 0), **DOM 변경 기록 수**(이론 최소), **diff ms**(할당 줄이기).

목표 수치(1k 기준, 측정 후 확정):

| 시나리오 | 지금 패치 / 기록 / diff ms | 목표 |
|---|---|---|
| 같은 데이터 다시 렌더 | 2000 / 0 / 17.6 | **0** / 0 / ≤ 6 |
| 10행마다 갱신 | 2100 / 100 / 21.7 | **100** / 100 / ≤ 8 |
| 한 행 선택 | 2001 / 1 / 27.7 | **1** / 1 / ≤ 8 (memo면 ≤ 1) |
| 빈 tbody에 생성 | 1000 / 1000 | 1000 / **1** |
| 1k 뒤에 1k 추가 | 3000 / 1000 / 466ms patch | 1000 / **1** / ≤ 150ms |
| 전체 지우기 | 1000 / 1000 | 1000 / **1** |
| 전체 교체 | 2000 / 2000 | 2000 / **≤ 2** |

## 3. 개선 후보 (예상 효과 · 측정 방법 · 위험)

우선순위는 "근거 수치가 큰 것, 설명하기 쉬운 것, 과제 제약과 충돌하지 않는 것" 순.

### P1-a. 벤치 하네스와 성능 예산 (mr-lead P1과 같음)
- `npm run bench` = `scripts/bench/run.js`(이미 작성). 결과는 `docs/bench/*.json`과 `docs/benchmarks.md` 표.
- 성능 예산 테스트 `tests/bench/budget.test.js`: 시나리오별 **패치 수·DOM 변경 기록 수 상한**(결정적이라 CI 가능). 시간은 기록만.
- 위험: 없음. 시간 수치는 환경을 함께 적는다.

### P1-b. 핸들러 교체를 PROPS 패치에서 빼기 (발견 1)
- 방법: 함수 → 함수 변경은 diff가 PROPS로 만들지 않는다. 대신 리스너가 "지금 커밋된 vnode의 props"에서 핸들러를 찾는다.
  구체안: patch가 노드를 만들 때 리스너를 한 번 달고, 리스너는 `dom`에 연결된 **핸들러 상자**(일반 JS 객체)에서 함수를 꺼낸다.
  상자 갱신은 diff가 아니라 patch 단계에서 한다(실패 복구 시 DOM과 핸들러가 어긋나지 않게). 함수 ↔ 함수가 아닌 값 변경(추가·삭제)은 지금처럼 PROPS.
  React도 같은 원리다: 핸들러는 fiber의 props에 있고, 이벤트가 날 때 그 props를 읽는다. 핸들러가 바뀌어도 DOM 작업이 없다.
- 예상: 같은 데이터 다시 렌더 패치 2000 → 0, 10행마다 갱신 2100 → 100, diff -10~15%.
- 측정: 벤치 패치 수, `tests/bench/budget.test.js`에 "패치 수 = DOM 변경 기록 수(핸들러 제외)" 불변식.
- 위험: 오래된 클로저 호출(stale handler) 버그 → "렌더 n번째 핸들러가 불린다" 테스트, fuzz에 핸들러 교체 추가. patch 목록을 보여 주는 데모(phase1·integrated)가 PROPS 개수에 기대는지 확인 필요.

### P1-c. 연속 삽입 묶기 · 전체 지우기 빠른 경로 (발견 3·4, mr-lead P1과 같음)
- 방법: **diff 출력(패치 목록)은 그대로 두고 patch 단계에서 합친다.** 같은 부모·이어지는 `before`를 가진 연속 CREATE는 `DocumentFragment`에 모아 `insertBefore` 한 번.
  부모의 이전 자식이 전부 REMOVE되면 `replaceChildren()`(또는 `textContent = ''`) 한 번. 전체 교체는 `replaceChildren(fragment)`.
  패치 목록이 같으니 학습 페이지의 패치 설명·개수와 기존 테스트 의미가 바뀌지 않는다.
- 예상: DOM 변경 기록 생성 1000 → 1, 덧붙이기 1000 → 1, 지우기 1000 → 1, 교체 2000 → 1~2. jsdom 시간: 덧붙이기 466 → ~150ms(이전 트리 없이 한 번에 넣는 경우가 111ms라는 근거).
- 측정: 벤치 기록 수·patch ms + **브라우저 벤치 페이지**(P2-a)에서 실제 레이아웃 포함 시간. 브라우저에서 이득이 없으면 기록 수만 주장한다.
- 위험: `<select value>`처럼 "자식 뒤에 속성" 순서에 기대는 경우(묶어도 PROPS는 CREATE 뒤라 유지되는지 테스트), `<template>` 자식(content에 넣기), 이어지는 CREATE 판정 실수 → fuzz에 "연속 CREATE·전부 REMOVE" 비율을 높인 시나리오.

### P1-d. diffChildren 빠른 경로 (발견 2)
- 방법 1: **key 없는 자식만 있는 부모**(대부분의 `<tr>`·`<td>`)는 Map·Set·이름 문자열·LIS 없이 위치끼리 바로 짝짓는다.
- 방법 2: **key 목록은 공통 접두·접미를 먼저 건너뛴다**(Vue 3·Inferno와 같은 방식). 가운데가 비면 남은 쪽만 CREATE·REMOVE, 남은 가운데에서만 Map·LIS.
  10행마다 갱신·선택·같은 데이터 다시 렌더는 순서가 그대로라 가운데가 비어 LIS·Map이 0번.
- 예상: `diffChildren`+`hasDuplicate`+`matchNames`가 diff 자기 시간의 약 45% → 같은 데이터 diff 17.6 → ~9ms.
- 측정: 벤치 diff ms, `--cpu-prof` 자기 시간 비교(스크립트로 남김).
- 위험: 중복 key 경고·위치 비교 대체 규칙을 빠른 경로에서도 지켜야 한다. 패치 순서(뒤에서부터, before가 제자리)가 바뀌면 안 된다 → 기존 diff 테스트 + fuzz.

### P2-a. 브라우저 벤치 페이지 `demo/bench/`
- js-framework-benchmark처럼 버튼: 1k 생성, 10k 생성, 1k 추가, 10행마다 갱신, 선택, swap, 삭제, 지우기.
- 시간: 클릭 → `performance.now()` → render → 다음 프레임(`requestAnimationFrame` 안에서 `setTimeout(0)`)까지 = 스타일·레이아웃·페인트 포함. 각 버튼 N회 중앙값.
- 같은 화면에 **패치 수·종류, MutationObserver 기록 수**, "innerHTML로 전부 다시 그리기" 비교 모드(같은 결과, DOM 변경 수와 포커스·입력 상태 유실을 대비해 보여 줌).
- 학습 포인트: "실제 DOM이 느린 이유(Reflow/Repaint)"를 숫자로 보여 준다. 강제 동기 레이아웃(삽입마다 `offsetHeight` 읽기) 토글로 하나씩 넣을 때와 한 번에 넣을 때 차이를 보여 준다.
- 위험: 브라우저마다 숫자가 달라 표에는 브라우저·버전·기기를 같이 적는다.

### P2-b. 순수 자식 컴포넌트 memo (선택적, 합의 필요)
- 과제 제약상 **자식은 props만 받는 순수 함수**다. 그러면 props가 얕은 비교로 같을 때 이전에 펼친 가상 트리를 그대로 돌려줘도 결과가 같다.
  지금 diff에는 이미 "이전과 같은 vnode 객체면 하위 트리를 건너뛴다" 경로가 있다. `memo(Row)`로 표시한 자식은 `expand`가 (부모 위치, key)별로 이전 결과를 기억했다가 같은 객체를 돌려주면 된다.
- 예상: 한 행 선택 diff 27.7 → 2행만 비교(< 1ms 목표), 10행마다 갱신 → 100행만 비교.
- 조건: 핸들러를 props로 넘기면 매번 새 함수라 memo가 무효 → `useMemo`로 핸들러를 고정하거나 id만 넘기는 패턴을 데모에서 보여 준다(React의 `memo`+`useCallback`과 같은 문제를 그대로 설명할 수 있음).
- 위험: API 추가(`memo`), 캐시 무효화 실수 → 기존 "vnode 객체 재사용" 테스트와 fuzz. 순수하지 않은 자식은 틀린 화면을 낸다(과제 규칙상 금지된 사용이지만 개발 모드 경고 고려). **합의 전에는 구현하지 않는다.**

### P2-c. 할당 줄이기 (발견 2)
- `createVNode`: `Object.defineProperty` → class `VNode` + 비공개 필드 `#dom` + `dom` getter/setter. JSON·`Object.keys`·`toEqual`에는 그대로 안 보인다(확인함: `JSON.stringify` → `{"type","props","children","key"}`).
  예상: 700k 생성 8~10배 빠름, 1k 렌더 트리 만들기 4.6ms → ~1.5ms, GC 감소.
- `collectNodes` 제거: "이전 트리의 노드인가"를 `vnode.dom != null`로 판정(이전 트리 노드는 커밋 후 모두 dom이 있다). diff마다 7,000개짜리 Set이 사라진다.
- `createDom`의 `deferLast(Object.entries(...))`가 요소마다 배열 3개를 만든다 → 루프 두 번으로.
- 측정: 벤치 diff ms, 프로파일 GC 시간.
- 위험: VNode 모양은 모든 모듈·테스트가 기대는 핵심. `isVNode`·`toStrictEqual`(현재 사용 0건)·structuredClone 사용처 확인. **mr-dx 동의 필요.**

### P3. 이벤트 위임
- 루트에 이벤트 종류마다 리스너 하나. 생성 1k에서 `addEventListener` 2,000번 → 0번.
- 위험이 크다: focus·blur·mouseenter·scroll처럼 버블링하지 않는 이벤트, `stopPropagation` 순서, 컨테이너 밖으로 옮긴 노드. P1-b로 핸들러 교체 비용은 이미 사라지므로 **이득(생성 시 리스너 등록 비용)을 먼저 재고, 10% 미만이면 하지 않는다.**

## 4. 실제 React·Vue와 비교 포인트 (학습 자료 소재)

| 주제 | 우리 (지금 → 제안) | React 18 | Vue 3 |
|---|---|---|---|
| key 목록 이동 | LIS: swap MOVE 2, 맨 뒤→맨 앞 MOVE 1 | `lastPlacedIndex`: 뒤에서 앞으로 옮긴 노드 기준이라 맨 뒤→맨 앞이면 나머지 999개를 옮김, swap(1↔998)이면 997개 이동 | 접두·접미 + LIS (우리 제안과 같음) |
| 공통 접두·접미 | 없음 → P1-d | 앞에서부터 key가 어긋날 때까지만 훑음 | 양쪽 모두 |
| 핸들러 변경 | PROPS 패치 → P1-b로 0 | props를 fiber에 두고 이벤트 때 읽음(루트 위임) | `invoker.value`만 바꿈(리스너는 그대로) — P1-b와 같은 방식 |
| 하위 트리 건너뛰기 | 같은 vnode 객체만 → P2-b `memo` | `React.memo`, 같은 element 객체면 bailout | 컴포넌트 단위 반응성 + 컴파일러 patch flag(정적 노드 호이스팅) |
| 대량 삽입 | 하나씩 → P1-c 묶기 | 새 하위 트리는 화면 밖에서 다 만든 뒤 맨 위 하나만 삽입. 목록에 덧붙이는 행은 하나씩 삽입 | 하나씩 삽입 |
| 전체 지우기 | 하나씩 → P1-c 한 번 | 하나씩 제거 | 하나씩 제거(배열 → 텍스트 전환 등 일부 경로만 한 번에) |

비교의 핵심 메시지: "우리는 React보다 빠르다"가 아니라, **같은 문제(목록 비교·핸들러·대량 삽입)에 React와 Vue가 고른 답이 각각 무엇이고, 우리는 무엇을 왜 골랐는지 숫자로 보여 준다.**
React 방식(`lastPlacedIndex`)과 우리 방식(LIS)을 같은 하네스로 돌리는 비교 구현은 mr-lead P3와 같다(시간이 남으면).

## 5. 위험 (정확성·가독성 비용)

| 위험 | 대응 |
|---|---|
| 빠른 경로가 코드를 설명하기 어렵게 만든다 | 빠른 경로마다 "왜·언제"를 주석 한 단락과 테스트 이름으로. 설명 자료(`docs/perf/*.md`)에 전→후 수치와 함께. 설명이 안 되는 최적화는 버린다 |

## 6. 다른 세션에 묻고 싶은 것

- mr-lead: 지표 셋(패치 수 = 실제 변경 수, DOM 변경 기록 수, diff ms)을 성능 예산으로 쓰는 데 동의하는지. P2-b `memo`를 과제 범위 안으로 볼지.
- mr-dx: P1-b(핸들러 상자)·P1-c(묶기)·P2-c(VNode 클래스)가 깨뜨릴 수 있는 엣지 케이스, fuzz에 넣을 비율. 핸들러 교체를 fuzz에서 검사할 방법.
