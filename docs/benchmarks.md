# 벤치마크

대량 목록(js-framework-benchmark와 같은 1,000행 표)을 조작할 때 mini-react가 하는 일을 숫자로 남긴다.

- 실행: `npm run bench` (1k, 11회 중앙값) · `npm run bench -- --rows 10000 --runs 1 --warmup 0` (10k)
  · `npm run bench -- --only swap` (시나리오 하나) · `--json docs/bench/<이름>.json` (원자료 저장)
- 성능 예산(CI): `tests/bench/budget.test.js`가 아래 결정적 지표 넷의 시나리오별 상한을 검사한다.
- 코드: `scripts/bench/scenarios.js`(시나리오·지표), `scripts/bench/run.js`(시간), `scripts/bench/react-moves.js`(이동 수 비교)

## 지표

| 지표 | 뜻 | 결정적? |
|---|---|---|
| 패치 | diff가 만든 패치 수 | 예 |
| 기록 | MutationObserver 기록 수 (DOM이 바뀐 횟수) | 예 |
| 붙임+뗌 | 기록 안 addedNodes + removedNodes 합 = 붙이거나 뗀 하위 트리 뿌리 수. 하위 트리를 통째로 붙이면 1, 옮기기 1번은 2 | 예 |
| 새 노드 | patch 뒤 컨테이너 안에 새로 생긴 노드 수 (만드는 API와 상관없이) | 예 |
| 이동 | 엔진의 MOVE 수 / LIS 이론 최소 / 같은 key 순서를 React식(`lastPlacedIndex`)으로 처리할 때 | 예 |
| diff ms, patch ms | 중앙값. **jsdom 기준 참고값**, 실행마다 ±30% | 아니오 |

측정 방식 주의: 실행마다 새 jsdom 창, 시나리오마다 새 Node 프로세스. 한 문서에서 계속 재면 남은 노드 때문에 삽입 시간이 2~3배 부풀고, 닫은 창도 메모리가 다 풀리지 않는다.
행의 핸들러는 실제 앱처럼 렌더마다 새 화살표 함수다.

## 기준선에서 읽은 것

1. **이동은 이미 최소다.** 엔진의 MOVE 수가 LIS 이론 최소와 같다. 같은 key 순서를 React식으로 처리하면 swap은 997번(10k는 9,997번), 맨 뒤 → 맨 앞은 999번 옮긴다. React는 "지금까지 제자리에 둔 노드 중 가장 뒤의 이전 위치"보다 앞에 있던 노드를 모두 옮기기 때문이다. 우리와 Vue 3는 LIS로 그대로 둘 노드를 고른다.
2. **핸들러 때문에 렌더마다 PROPS가 행마다 2개 생긴다.** 같은 데이터로 다시 그려도 패치 2000개, DOM 변경 0. 갱신 시나리오의 diff 시간(13~15ms) 대부분은 DOM을 바꾸지 않는 비교 작업이다.
3. **빈 tbody 생성·덧붙이기·지우기는 행마다 DOM 연산 1번**(기록 1000). jsdom에서는 자식이 많은 부모에 하나씩 넣고 빼는 비용이 행 수보다 빠르게 커진다(10k 덧붙이기 10초, attach 지우기 43초). 브라우저에서도 그런지는 브라우저 벤치 페이지에서 따로 잰다.

개선 계획과 순서는 `docs/decisions/0001-plan.md`(ADR 0001)를 따른다. 최적화 브랜치는 이 표에 "변경 전 → 후"를 더하고 예산 상한을 낮춘다.
